## 二、问题分析与方案设计

### 2.1 痛点调研

与 8 位同学交流后确认，校园课表场景存在三个真实痛点：

| 痛点 | 具体表现 | 影响 |
|---|---|---|
| **忘记看课表** | 早上出门前没有确认当天安排 | 迟到、走错教室 |
| **查课表麻烦** | 需登录教务系统，多层点击，手机上体验差 | 时间成本 |
| **周次差异** | 同一星期不同周次的课程不同（如第 12 周起某课结束） | 记错上课安排 |

用户在反馈中直接印证了这三点：

> "很好地解决了容易忘记上课时间地点的问题"（用户 3）
> "不用自己点课程表看了"（用户 8）

### 2.2 方案选型

| 备选方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 手机 App | 体验好 | 开发成本高，需上架 | ❌ |
| 微信小程序 | 免安装 | 需企业主体、审核周期长 | ❌ |
| 网页版 | 跨平台 | 需部署服务器、域名 | ❌ |
| **邮件提醒** | **零安装、零成本、手机原生推送** | 需手动维护课表 | ✅ **采用** |

**选择邮件的核心理由**：邮箱是每个学生都有的、手机自带推送的、无需额外配置的通知渠道。用户只需在早上看一眼邮件即可。

### 2.3 技术架构

```
┌─────────────────────────────────────────────────────────────┐
│  GitHub Actions（每天 UTC 23:30 = 北京 07:30）              │
├─────────────────────────────────────────────────────────────┤
│  1. checkout 代码                                            │
│  2. setup-python 3.11 + pip install pandas                   │
│  3. 运行 main.py                                             │
│       ├─ 读取 schedule.csv（支持周次表达式）                  │
│       ├─ 计算当前周次（学期起始 + 天数差）                     │
│       ├─ 筛选当天当周课程                                     │
│       ├─ 构造邮件正文                                         │
│       └─ SMTP_SSL(465) 登录 QQ 邮箱发送                       │
│  4. 追加日志到 process_logs/daily_log.txt                     │
│  5. git commit + push 日志回仓库                              │
└─────────────────────────────────────────────────────────────┘
```

**关键技术决策**：

| 决策 | 原因 |
|---|---|
| **用 UTC 23:30 而非北京 7:30** | GitHub Actions 使用 UTC，23:30 UTC = 次日 07:30 北京时间 |
| **代码显式使用北京时间** | 云端 `datetime.now()` 返回 UTC，会算错星期；必须用 `timezone(timedelta(hours=8))` |
| **日志写 JSON 风格的行数据** | 一行一条便于 grep、统计与人工核对 |
| **日志不含课程名/教室/教师** | 仓库公开，避免隐私泄露；只记录课程数 |
| **空提交时正常退出** | `git diff --cached --quiet && exit 0`，避免无变更时 Action 变红 |

### 3.2 迭代 1：日志中文乱码修复

**现象**：程序正常运行，日志写入成功，但在 PowerShell 中查看时中文全部乱码（`甯濇湡=鍛戒竴`），英文与数字正常。

**定位过程**：
- 英文正常、中文乱码 → 文件本身没坏，是读取方式问题
- 用 Python 打开文件能正确读到中文 → 写入端正确
- 乱码形态是 "UTF-8 字节按 GBK 解释" 的典型特征

**根因**：PowerShell 5.x 的 `Get-Content` 默认按系统 ANSI 代码页（简体中文为 GBK/CP936）解码文件，而日志是 UTF-8。

**修复**：`Get-Content daily_log.txt -Encoding UTF8`，并把查看方式写入文档。

**证据**：`screenshots/day1-log-bug.png`（修复前乱码）vs `day1-log.png`（修复后正常）

### 3.3 迭代 2：课表支持周次维度

**现象**：程序上线后，用真实课表核对时发现，同一星期不同周次的课程不同：
- 星期四 7-8 节「职业生涯规划」只在 3-6、8-11 周有，第 12 周起消失
- 星期二 7-8 节：8-11 周是「形势与政策I」，12-13/16/17/18 周是「思想道德与法治」
- 星期三 7-8 节「大学生心理健康」只在 3、6、9、12、17 周（每 3 周一次）
- 第 14、15 周军训，所有课程停课

**根因**：原始数据模型是「星期 → 课程列表」的二维关系，而实际课表是「周次 × 星期 → 课程」的三维关系。这是需求调研不充分导致的设计缺陷。

### 3.4 迭代 3：日志追加时行粘连

**现象**：首次定时任务后，`daily_log.txt` 第 4、5 行粘连成一行：

```
...耗时=1070ms2026-11-02 07:58:10 | trigger=schedule | ...
```

**根因**：`write_log()` 以 append 模式写入，未检查文件末尾是否为换行符。当文件由 git 冲突手工合并产生且末尾无换行时，新记录会接到上一行。

**修复**：

```python
# 追加前先检查文件末尾是否为换行符
needs_newline = False
if os.path.exists(LOG_PATH) and os.path.getsize(LOG_PATH) > 0:
    with open(LOG_PATH, "rb") as f:
        f.seek(-1, os.SEEK_END)
        needs_newline = f.read(1) != b"\n"

with open(LOG_PATH, "a", encoding="utf-8") as f:
    if needs_newline:
        f.write("\n")
    f.write(line)
```

**验证**：构造末尾无换行的日志文件，运行后新增记录正确换行，四种边界场景（有换行/无换行/文件不存在/空文件）全部通过。

### 4.4 关于执行延迟的说明

GitHub Actions 免费版的定时任务存在排队延迟，实际执行时间比设定的 07:30 晚 28～35 分钟，属正常现象。

**延伸观察**：11-10 之后延迟逐渐增大到 3-5 小时（10:54～12:44）。这是平台资源调度问题，不影响程序功能，但如果是真实生产场景，应考虑改用云服务器 crontab 或付费的 Actions 分钟数。

## 七、经验总结

### 7.1 做对了什么

1. **先用最小可用版本跑起来，再迭代**
   最初版本只有"按星期筛选 + 发邮件 + 写日志"，但能立刻上线运行。先有日志数据，再谈优化。

2. **真实数据比构造数据更能暴露问题**
   迭代 2 的问题只有用真实学期课表才暴露；迭代 4 的编码问题只有真实用户用 Excel 操作才会遇到。

3. **用户反馈要分类处理**
   8 份反馈里，"很好用"和"卡在 UTF-8"价值完全不同。后者直接指向可执行的产品改进。

4. **工程决策以"能跑" 为第一优先级**
   onefile 打包理论上更优雅，但被 Defender 拦截——换成 onedir 虽然需分发文件夹，但能正常运行。

5. **隐私保护前置设计**
   日志从一开始就不记课程内容，避免了后期脱敏改造。

### 7.2 做得不够好的

1. **需求调研不充分**
   迭代 2 的周次问题说明：开发前应把"课表的结构"问清楚，而不是假设"每周都一样"。

2. **UI 设计能力不足**
   第一版界面确实朴素，被用户直接指出。如果提前参考成熟的设计规范（如 Material Design），可以减少一轮返工。

3. **打包方案没有提前验证**
   onefile 的问题在上线前才暴露。理想做法是打包后立即在目标环境测试。

4. **GitHub Actions 的延迟预估不足**
   README 里写"7:30 执行"，实际延迟 30 分钟甚至几小时，应在文档里提前说明。

### 7.3 如果重做会怎么做

| 阶段 | 改进 |
|---|---|
| **调研** | 先收集 3 份不同的教务系统课表，确认所有变化维度（周次、单双周、军训、节假日）|
| **设计** | 课表数据模型直接按"周次 × 星期 × 节次"设计，避免二次重构 |
| **UI** | 第一版就用统一的配色与圆角控件，减少返工 |
| **打包** | 打包后立即在干净环境测试，确认无杀软拦截 |
| **发布** | 先找 1-2 个同学试用，收集问题后再批量分发 |

## 九、结论

本项目完整实现了"每日课表邮件提醒"这一校园实用工具，并通过 **7 天连续自动化运行日志**、**4 次有据可查的迭代**、**8 位真实用户反馈**，形成了完整的"发现问题 → 改进 → 验证"闭环。

**最核心的收获不是代码本身，而是验证了一个方法论**：

> **真实用户反馈是产品改进最可靠的依据。**

迭代 1-3 都是我自己在调试中发现的问题，属于"程序能不能正确运行"；而迭代 4 完全来自用户——CSV 编码会让普通同学卡住，界面朴素会影响第一印象。这些问题在开发者视角里是"不是问题"，在用户视角里却是阻塞。

**下一步可延伸的方向**：

1. **接入教务系统**：若能获取课表 API，可省去手动维护 CSV 的负担；
2. **多渠道推送**：除邮件外增加微信服务号模板消息、企业微信机器人；
3. **课前提醒服务化**：将课前 N 分钟提醒从"手动检查"升级为服务端定时推送；
4. **多用户支持**：当前用户版需各自配置，可做成有后端的多用户系统。
