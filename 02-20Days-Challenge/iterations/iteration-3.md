# 迭代 3：日志追加时行粘连修复

- **日期**：2026-11-02
- **触发方式**：首次定时运行后检查日志发现
- **涉及文件**：`main.py`（`write_log` 函数）、`process_logs/daily_log.txt`（数据修复）
- **证据**：定时运行日志、修复前后对比

---

## 一、现象

2026-11-02 首次定时任务（`trigger=schedule`）成功运行并自动提交日志后（commit `aea82d4`），检查 `daily_log.txt` 发现：

第 4 行和第 5 行**粘连成了一行**：

```
2026-11-02 01:44:38 +0800 | trigger=local | SUCCESS | 周次=9 | ... | 耗时=1070ms2026-11-02 07:58:10 +0800 | trigger=schedule | SUCCESS | 周次=9 | ... | 耗时=3391ms
                                                    ↑ 这里应该有换行
```

文件物理行数错误：**5 条运行记录只占 4 个物理行**。

## 二、定位过程

| 观察 | 推断 |
|---|---|
| 粘连点刚好在 `耗时=1070ms` 和下一个时间戳之间 | 追加写入时，前一条记录末尾缺少换行 |
| 前一条记录（01:44:38）是**冲突解决时手工写入**的 | 手工写文件时末尾没有 `\n` |
| `write_log()` 中 `line` 本身以 `\n` 结尾 | 单条记录格式没问题，问题在**追加前** |
| 后续 schedule 运行时正常追加，只是接在了同一行 | Python 的 `open(..., "a")` 不会自动补换行 |

**结论**：`write_log()` 直接以 append 模式写入，**未检查文件末尾是否为换行符**。当文件由外部（如 git 冲突手工合并）产生且末尾无换行时，新记录会粘连到上一行。

## 三、根因

```python
# 修复前
with open(LOG_PATH, "a", encoding="utf-8") as f:
    f.write(line)          # line 以 \n 结尾，但只保证本条记录结束有换行
```

**缺省假设**：「文件末尾一定是干净的换行边界」，但该假设在以下场景不成立：

1. git 冲突手工合并文件（本次情况）
2. 其他工具/编辑器写入日志
3. 上次写入因进程被强制终止而中断

追加型日志的健壮写法必须**在写入前自检边界**。

## 四、修复

### 1. 代码修复：写入前检查末尾换行

```python
    # 追加前先检查文件末尾是否为换行符，避免新记录与上一行粘连
    needs_newline = False
    if os.path.exists(LOG_PATH) and os.path.getsize(LOG_PATH) > 0:
        with open(LOG_PATH, "rb") as f:
            f.seek(-1, os.SEEK_END)
            needs_newline = f.read(1) != b"\n"

    with open(LOG_PATH, "a", encoding="utf-8") as f:
        if needs_newline:
            f.write("\n")
        f.write(line)
```

**要点**：
- 以**二进制**模式读取末尾 1 字节，避免文本模式换行转换的干扰
- `seek(-1, os.SEEK_END)` 定位到最后 1 字节，性能不受文件大小影响
- 文件不存在或为空时跳过检查

### 2. 数据修复

将 `daily_log.txt` 中粘连的第 4 行拆分为两条独立记录：

```diff
- ...耗时=1070ms2026-11-02 07:58:10 +0800 | trigger=schedule | ... | 耗时=3391ms
+ ...耗时=1070ms
+ 2026-11-02 07:58:10 +0800 | trigger=schedule | ... | 耗时=3391ms
```

数据内容未做任何改动，仅修复行边界。

## 六、对比

| 项 | 修复前 | 修复后 |
|---|---|---|
| 末尾无换行时追加 | ❌ 与上一行粘连 | ✅ 自动补换行 |
| 日志物理行数 | 5 条记录占 4 行 | 5 条记录占 5 行 |
| 对 git 日志的兼容性 | ❌ 依赖文件末尾干净 | ✅ 任意状态均可追加 |
| 性能影响 | — | 每次多一次 `seek`+`read(1)`，可忽略 |

## 七、经验与后续

1. **追加型日志不能假设文件边界**：外部工具、手工合并、进程中断都可能留下不完整的最后一行。
2. **用二进制读取做边界检查**：文本模式在 Windows 上会把 `\r\n` 当作换行，判断不准确。
3. **这类问题只在「外部写入 + 自动追加」交叉时暴露**：如果一直是程序自己写日志，可能永远不会发现问题——**这次是 git 冲突手工合并触发的**。
4. **后续可考虑**：日志文件按月轮转，避免长期运行后单文件过大；或在写入时增加文件锁，防止并发写。
