# VS Code 接入内网模型 qwen3.5-122b 排障

- 时间：2026-10-21 19:00 – 21:00
- 使用模型：Qwen / DeepSeek-Chat
- 环境：Windows 11 / VS Code 1.141.0（安装在 `D:\visual studio code\`，中文界面）
- 结论：**部分解决** —— 配置链路全部打通，但内网端点在本机不可达，需连内网/VPN

## 1. 现象（原始报错）

想在校内网里用 `qwen3.5-122b` 辅助写课题10 的脚本。端点信息：

```
Base URL : http://10.1.88.114:8001/v1
Model ID : qwen3.5-122b
API Key  : EMPTY（内网不校验）
```

实测结果：

```
Test-NetConnection 10.1.88.114 -Port 8001
  → TcpTestSucceeded : False

ping 10.1.88.114
  → 请求超时

curl http://10.1.88.114:8001/v1/models
  → curl: (7) Failed to connect ... 拒绝连接
```

关键判断依据：**同一时刻访问 `www.baidu.com:443` 正常**，所以不是断网。

VS Code 侧另外还发现两个坑（即使网络通了也会报错）：

1. `~/.continue/config.json` 是旧版格式，Continue 1.x 已改用 `config.yaml`；
2. 旧配置里把 `qwen3.5-122b` 当成 embedding 模型和 Tab 补全模型，
   前者会持续报错重试，后者会让编辑器卡顿。

## 2. 我的提问（原文）

> 我在学校内网里要接入 `http://10.1.88.114:8001/v1` 的 qwen3.5-122b，
> 但 ping 和 8001 端口都不通，同时我能正常上百度。
> 另外我 `.continue` 目录里已经有一份 config.json，是不是直接改就行？

## 3. AI 给的方案

1. **先分层定位**：`10.1.x.x` 是私有地址，只能在特定局域网/VPN 内可达。
   先用 `Test-NetConnection ... -Port 8001` 区分「断网」和「这个地址到不了」两种情况。
2. **确认真实 model id**：别人给的 `qwen3.5-122b` 不一定是服务端注册的 id，
   必须 `curl /v1/models` 看返回里的 `"id"`，**差一个字符就是 400 报错**。
3. **清旧配置再建新配置**：把 `config.json` 改名为 `config.json.bak`（不要直接删），
   新建符合 1.x 的 `config.yaml`，避免旧配置自动迁移和新配置打架。
4. **别拿 chat 模型当 embedding / Tab 补全模型**。
5. **验证请求是否真的到达端点**：vLLM 暴露 `/metrics`，
   其中 `vllm:request_success_total` 是累计计数器，
   发一次请求前后对比计数即可证明请求确实打到了服务端。

## 4. 我实际做了什么

1. 按第 1 条做分层验证，确认是「内网地址不可达」而非本机断网
   （`ping 10.1.88.114` 超时 + `www.baidu.com:443` 正常）。
2. **把第 5 条做成了脚本** `verify-qwen-endpoint.ps1`：轮询 `/metrics` 计数器，
   在 VS Code 里重载窗口并发一条消息，若计数增加即证明请求送达。
   这样避免「以为通了其实没通」。
3. 按第 3 条处理旧配置：`config.json` → `config.json.bak`，
   新建 `config.yaml`，把 `roles` 限定为 `chat/edit/apply`，
   并显式配 `noProxy: [10.1.88.114]`、`timeout: 600`。
4. `model:` 一项**先留占位**，计划等 `/v1/models` 能通后再照抄真实 id。

网络这一步**没有解决**：本机不在该内网/VPN 内，`10.1.88.114:8001` 始终不可达，
所以模型至今未能真正对话。

## 5. 结果与证据

- 连通性实测记录：`TcpTestSucceeded: False`，`ping` 超时，`curl` 拒绝连接
- 配置产物：`config.yaml`（已就绪）、`config.json.bak`（旧配置备份）
- 验证脚本：`verify-qwen-endpoint.ps1`，用法：
  ```powershell
  powershell -NoProfile -ExecutionPolicy Bypass -File .\verify-qwen-endpoint.ps1
  ```
  通过时输出 `PASS: endpoint received N new request(s)`；
  未通过时按顺序提示检查重载窗口、模型下拉、输出面板日志、配置文件
- 完整操作手册：`vscode-接入内网模型-操作手册.md`（含第 7 节报错对照表）
- 相关痕迹：`chatLanguageModels.json`、`continue-config.yaml`、`nettest.js`、`probe-endpoint.js`

## 6. 复盘

- **结论要说准确**：这件事的状态是「配置已就绪、网络受限」，
  不写成「已解决」。`10.1.x.x` 在没有 VPN 的机器上就是不可达，
  这不是脚本能绕过的，属于环境前提。
- **AI 方案里最有价值的一条**：用 `/metrics` 计数器验证请求是否真的到达。
  没有它，「VS Code 一直转圈」到底是网络问题、配置问题还是模型慢，
  完全无法区分。
- **AI 方案里最容易踩的一条**：`model:` 必须与服务端 id 一字不差。
  我一开始就想直接照抄别人给的 `qwen3.5-122b`，被提醒后才决定先用占位符。
- **自己补的一条**：`config.json` 要改名而不是删除，
  否则一旦新配置有问题就回不去了，和 hosts 那个排障是同一个思路。
- **遗留项**：拿到内网访问后，第一步先跑
  `curl http://10.1.88.114:8001/v1/models`，把真实 id 填进 `config.yaml`，
  再跑 `verify-qwen-endpoint.ps1` 确认。
