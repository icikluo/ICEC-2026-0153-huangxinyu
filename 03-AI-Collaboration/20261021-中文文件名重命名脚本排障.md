# 课题10：中文文件名批量重命名脚本排障

- 时间：2026-10-21 18:40 – 21:10
- 使用模型：DeepSeek-Chat
- 环境：Windows 11 / Python 3 / 目录 `stage1-task10`
- 结论：**已解决**（正确率 10/10）

## 1. 现象（原始报错）

课题10 的任务是「图片文件按内容类别批量重命名」，样本里有 5 个脏数据（括号副本、
同名不同后缀、大写扩展名、中文前缀）。第一版脚本 `rename_tool.py` 试跑时报错：

```
UnicodeEncodeError: 'gbk' codec can't encode character '\u2705' in position 0:
illegal multibyte sequence
```

以及执行后计数对不上：

```
预期 10 个文件重命名成功，实际 9 个
IMG_0040.jpg 与 IMG_0040.png 冲突
```

第二个问题更麻烦：**主名相同的两个文件，被脚本判成「重名冲突」而跳过**。

## 2. 我的提问（原文）

> 我用 Python 批量重命名，文件名里有中文（美食/风景/物品），一直报
> `UnicodeEncodeError: 'gbk' codec`。
> 另外我的样本里 `IMG_0040.jpg` 和 `IMG_0040.png` 主名一样、后缀不同，
> 脚本认为冲突直接跳过，但我认为它们应该各自编号。怎么改？

## 3. AI 给的方案

1. **编码报错**：Windows 控制台默认 GBK，打印 emoji 或部分中文字符会崩。
   解决办法是给脚本加 `# -*- coding: utf-8 -*-`，并对 `stdout` 重新包装成 UTF-8，
   或者打印时避免 emoji。
2. **「重名冲突」判断错**：覆盖判据必须用**含扩展名的完整文件名**去比对，
   而不能只比主名。`IMG_0040.jpg` 和 `IMG_0040.png` 是合法的两个不同文件。
3. **中文路径**：读写文件统一用 `pathlib`，避免手写字符串拼接导致的路径问题。
4. 建议加一个**预演（dry-run）+ 映射表导出**步骤，重命名前先产出 `old → new`
   对照表，人工确认无误再真正执行，并提供回滚。

## 4. 我实际做了什么

1. 采纳「完整文件名比对」这条核心修改：判据从主名改成含扩展名的全名。
2. 采纳「预演 + 映射表」：脚本先输出 `rename_mapping.csv`，确认后再 `--execute`。
3. **没有采纳**「加 emoji 避免崩溃」这条——我直接去掉了所有 emoji 输出，
   改成纯文本 `[OK] / [SKIP]`，因为在 GBK 控制台下治标不治本。
4. 额外做了一件 AI 没提的事：**固定处理顺序为原文件名自然排序**
   （与资源管理器「名称升序」一致），否则编号会随系统枚举顺序漂移，
   人工组和 AI 组的结果无法比较。

## 6. 复盘

- **两个报错其实是一个根因的两面**：都是「把文件名当纯文本处理」而没有考虑
  「编码」和「扩展名属于名字的一部分」。
- **AI 方案里最关键的一条**：用完整文件名做覆盖判据。这条直接决定了正确率
  能否从 9/10 变成 10/10。
- **AI 方案里我否掉的一条**：绕开 emoji。绕开症状不等于修好编码问题，
  改掉输出更干净。
- **我自己补的一条**：固定排序。对比实验里如果枚举顺序不稳定，
  两组数据就没有可比性——这一点 AI 没提醒，是我做实验时才意识到的。
- **对课题本身的意义**：AI 一次生成能跑通的脚本，但脏数据边界要人来兜底，
  这正是《提交件⑤ 人机校验规则》要写的东西。
